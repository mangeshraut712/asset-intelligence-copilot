# Asset Intelligence Copilot: System Design (page 1, draft)
*Mangesh Raut · FlytBase challenge, AHC × Hacktoberfest 2026 · github.com/mangeshraut712/asset-intelligence-copilot*

**Idea.** Numbers come from code, and language comes from the model. A deterministic, tested tool layer computes every fact. A router (rules first, LLM second) picks the tool and the visual. Every answer carries the record IDs and documents it used.

**Storage and indexing.** `loader.py` reads one or more dataset folders into SQLite and can be re-run safely. It loads wells, equipment, inspections (indexed by well and date), maintenance, regulator events, notes and documents. It follows each repair's `report_file`, stores the report text, and parses facts that exist only in prose, such as *"contained about 7.1 hours"*. It also parses thresholds and deadlines from the manuals and SOPs into a `rules` table instead of hard-coding them: producing Δ ≥ 15 °C for T200 and 20 °C for T350, reportable ≥ 5 bbl, notice ≤ 24 h, containment ≤ 4 h, verification ≤ 60 d, NOV response ≤ 30 d, and RCA at 3 repairs. Reloading rebuilds the raw tables and keeps the runtime memory tables. The test dataset loads with one command, alongside the sample or on its own.

**Tools (all deterministic and unit-tested).** `effective_inspections` is the single source of truth. It overlays correction notes (voided spills) and runtime corrections onto the raw readings and keeps the originals. On top of it: `well_status`, `area_not_producing`, `temp_series`, `spills`, `downtime` (7 days per non-producing weekly inspection, with causes from overlapping repairs and dated notes), `downtime_ranking`, `spill_heatmap`, `spill_compliance`/`compliance` (SR-01/02/03, RC-02, RC-04, RCA), `containment_breaches`, `reportable_spills`, `rca_check`, `repair_costs`, `repairs`, `spill_detail` and `search_docs` (keyword retrieval over manual and SOP sections). Periods are resolved against a configurable "today", ending yesterday.

**Combining numbers, documents and notes.** Each tool joins the records. For example, a spill's compliance check takes the inspection, its regulator events, the triggering repair, the containment hours parsed from that repair's report, and the SOP limit. Notes add reasons ("planned shut-in, not yet in the maintenance system"). The recorded status is shown, then flagged when the inspections disagree with it.

**Agent and generative UI.** The rule router (intent regexes plus entity extraction for wells, areas, periods and visuals) is authoritative when it matches confidently. When it is unsure, an LLM makes one function call to pick an intent and rewrite the question with explicit entities. The deterministic tools still compute the answer, so the LLM can never invent a number. A visual the user asks for overrides the default (card, table, line, bar, map or heatmap). The FastAPI backend serves a single-page UI (Chart.js and Leaflet) with a user picker and a live memory panel.

**Memory.** *Private:* each Q&A is stored with the user, chat, timestamp and the wells it mentioned, so "the wells we discussed yesterday" resolves only from that user's earlier chats. Another user gets "no earlier conversation". *Shared:* statements about a well become attributed well facts that every user sees. *Feedback:* corrections to raw data or to the AI's analysis are stored per inspection and field, with the original value, author, reason and timestamp, and applied in every later query for every user. The affected rules are then re-evaluated; for example, 4.5 → 5.4 bbl makes the spill reportable and raises SR-01 and SR-03 duties. Type-wide rules ("all T350 wells: RCA after 2") apply to that well type only, and answers say they follow the user's rule, not the manual.

**Conflicts.** A statement is checked against the latest inspection. If they disagree, it is stored as *unconfirmed*, and the copilot names the inspection, shows which other user's note agrees, and asks for confirmation. A correction that contradicts an inspector note is applied but flagged. Disagreeing notes are shown side by side; only a formal correction overrides a detection.

**New data.** Nothing is tied to the 200 sample wells. Rules are parsed, areas and users are read from the data, and file paths are followed rather than guessed. The question runner (`eval/run_questions.py`) takes a .txt or .json file and writes Markdown and JSON answers.

**Models and cost.** The core needs no model and costs $0. Optional routing uses free OpenRouter models (Gemma 4 31B → Gemma 4 26B → Nemotron 120B fallback chain). Each new question costs at most one call, answers are cached on disk, and any failure falls back to the rule router. Scores on the 18 examples (27 checks): rules 27/27, LLM-forced 27/27.

**Next.** Embedding retrieval over the repair reports, LLM-written prose on top of tool JSON (with a check that the numbers are unchanged), multi-turn follow-ups, and an evaluation harness on the test set.
